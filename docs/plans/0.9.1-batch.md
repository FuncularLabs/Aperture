## What the code says about the items (premise checks)

- **Quick view doesn't play videos.** For a video it shows the item's large thumbnail (a still frame); there is no
  media player anywhere in the app. Items 1 and 2 presume playback, so this batch adds it.
- **Indexing already runs off the UI thread** (`LibraryService.IndexRootAsync` runs the indexer in `Task.Run`). The
  freezes come from work each run hands back to the UI thread, which grows with the library:
  - while a new folder streams in, every 1.2 s: `LoadRows()` (every row the library shows) and `BuildViewImmediate()`
    (the whole grid's filter, sort and sections), both synchronous;
  - once a second per folder: `CountForRoot` (a SQL count) for its climbing count;
  - at the end of every run that changed something (every watcher re-index too): `CountForRoot`, `LoadRows()`,
    `BuildTree()` and `SelectPath`. `BuildTree` walks every row once per root, and `LoadChildNodes` again for each
    folder it re-expands, so a tree with many expanded folders costs rows × folders.
- **The library's one FunkyORM provider is shared between threads** (`ApertureDatabase.Provider`). A transaction opened
  on it on the UI thread (removing a folder, saving tags) is seen by any read on another thread meanwhile, which then
  throws and ends Aperture (`docs/plans/multiple-libraries.md` revisions 25–26; open for Paul since 0.9.0). Moving the
  reads above off the UI thread would hit this on every indexing run, so this batch fixes it: off-thread reads use a
  provider of their own. FunkyORM keeps a transaction per provider object and opens a connection per operation
  outside one (3.10.1 `SqliteOrmDataProvider.ConnectionScope`), so a provider that never begins a transaction never
  joins one.
- **Library counts:** a library that isn't open shows `CatalogEntry.ItemCount`, recorded only when the user switches
  away from it or quits with its items read. A library opened with **Open library…**, or one not left since 0.9.0
  shipped, has none.
- The batch says the last tag is v0.8.9; it is **v0.9.0** (released 2026-11-11). The csproj says 0.9.0.

## Acceptance criteria

### Quick View video (items 1, 2)

- **V1** Quick view plays a video: opened on a video, or moved to one, it starts playing it. The still frame shows until
  the video's first frame is ready; a video that hasn't opened yet says "Loading video…". A video that can't be played
  (no codec, the file unreachable, no media player on this PC) keeps the still frame, with a line saying it can't be
  played here and that `Enter` opens it in its default app.
- **V2** On a playable video, `Space` and a single click on the video toggle play and pause (before it has opened, they
  set whether it plays once it has). The video is the still frame's area, the video's own once it has opened, or the
  whole area while it has neither. A press beside the video closes quick view, as for photos; `Esc` closes; `Enter` or
  a double-click opens it in its default app and pauses it. On a photo, or a video that can't be played, `Space` closes
  quick view, as before.
- **V3** A video that reaches its end stops there, paused; `Space` or a click plays it again from the start.
- **V4** Quick view shows a playable video's controls: play/pause, mute/unmute and a volume slider (0–100 %). Raising
  the volume while muted unmutes, as Windows' own volume does.
- **V5** The first video Aperture ever plays starts muted (volume 50 %). Every video after that starts with the mute
  state and volume the user last left, also after Aperture restarts and in any library. A missing, unreadable or
  corrupt preferences file counts as "never played": muted. A mute is saved at once; a volume set while a video plays
  is saved as it's left (another item, quick view closed, a switch, the window closed). Tests never touch the user's
  real file.
- **V6** Leaving a video (another item, closing quick view, a library switch, quitting) stops it and releases its
  file: it can be renamed or deleted at once. A photo shown after a video is silent at once, before it has decoded.
  Zoom does nothing on a video.
- **V7** Each visit is its own: moving between two videos, or reopening quick view on the video it was closed on,
  plays the one now shown; the still frame arriving doesn't stop it; a player event (opened, ended, failed) from a
  video already left changes nothing.
- **V8** A PC without a media player still opens Aperture and quick view; its videos show their still frames with the
  V1 line. Quick view's hint line names the video keys while a video is shown; the README and the CHANGELOG describe
  playback.

### Indexing (items 3, 4)

- **I1** While folders are indexed, the UI thread does none of the reads the run triggers: the grid's refresh as
  thumbnails stream in, a folder's climbing count, and the refresh when a run ends (rows, counts, folder index) all
  read and compute on a background thread; the UI thread only applies the results.
- **I2** A slow read doesn't stop the window: while such a read is in progress, the window still handles input.
- **I3** Refreshes coalesce, and none is lost: a refresh asked for while one runs is done after it, with the union of
  what both asked for (rows, the tree, which folders' counts). A run's end is never dropped because another folder's
  refresh came after it.
- **I4** A stale read never undoes a change: rows read before the user hid, showed, included, excluded or removed a
  folder (or pressed F5), or before the startup read, aren't shown; the newer rows stay and the read is done again if
  it was asked for. The startup read does the same (it used to assign its rows unchecked, from 0.8.9).
- **I5** An off-thread read never joins or breaks a change on the UI thread: a read while a folder is removed or tags
  are saved succeeds and sees only what's committed. A read that fails keeps the rows the window had. A library being
  closed (switch, exit) waits for its reads in flight, so its files can be deleted straight after.
- **I6** The folder tree is built from one pass over the rows (a `FolderIndex`, rebuilt whenever the rows change):
  expanding a folder, or restoring the folders left expanded, reads the index, not the rows. It shows the same
  folders, order and counts as before.
- **I7** Counting first: when a folder is added or a change is detected, the scan counts the files before any is
  indexed, and the window shows the count climbing ("Counting files in Photos… 12,345 so far"), then the run's
  progress ("Indexing Photos: 1,234 of 12,345 files") from its first file (a report as soon as the count is known,
  then at most every quarter of a second, and at each batch saved), however few files there are. Two runs of one
  folder at once (its watcher fires during a run) are one folder, said by the newer run.
- **I8** While anything is indexed, a progress bar spans the bottom of the window (filling once the count is known,
  moving while counting), with the line "This might take a while. You can keep browsing." When some of the files the
  run will read are online-only (cloud placeholders), it adds how many: they're downloaded as they're read. Files the
  run skips (unchanged) aren't counted. The indexing card shows the same lines. Pause, Stop and Resume work as before.

### Sidebar (items 5, 6)

- **S1** Libraries can be dragged into a new order in the LIBRARIES list, kept across restarts and every other change
  to the list. A library added later goes at the end. Until the user moves one, the list stays alphabetical, as
  before (the current culture's order, ignoring case).
- **S2** Folders at the top level of FOLDERS can be dragged into a new order, kept per library across restarts. A
  folder added later goes at the end; until the user moves one, alphabetical as before (ordinal, ignoring case).
  Subfolders keep their names' order. Moving a folder keeps it (and what it's doing: indexing, paused), its
  expansion, and the selection.
- **S3** A drag starts only once the pointer moves past the system's drag distance. A drag of a library never switches
  to it; pressing a folder selects it, as before, and a drag then moves it. Dropping a library or folder on its own
  place, outside the list, or pressing `Esc` changes nothing and writes no order. A reorder drag never adds a folder
  (the window's drop of folders from Explorer is unaffected).
- **S4** A malformed order (hand-edited, or from another version) is ignored: the libraries and every other setting are
  kept. An older Aperture ignores the orders, and drops them the next time it saves the file.
- **S5** Every library shows its item count whether or not it's open: the open one its live count (as before), each
  other one the number of items it shows when open (its included folders' items, less those in hidden subfolders),
  read from its own files in the background, one library at a time, so a library never left since 0.9.0 has one too.
  The count read is remembered for the next launch. A library whose files can't be read keeps the count it had, or
  none; a count from an older refresh lands nowhere.
- **S6** Reading another library's count changes nothing in it and doesn't hold it open: it creates no database where
  none is, opens it read-only and closes it (no pooled connection). **Delete library files** waits for a count read of
  that library in flight, so it deletes everything.

## Decisions made without asking (defaults; listed for Paul)

1. Quick view plays a video as soon as it's shown (as Photos does); muted the first time (V5).
2. `Space` on a video plays and pauses (the batch's ask); `Esc` closes. On photos `Space` still closes, as before.
3. No zoom on videos; no seek bar or time display (not asked: offered as a follow-up).
4. Mute and volume are app-wide, kept in `playback.json` beside the library list (`%LocalAppData%\Aperture
   Libraries`), or in the library's own folder when `APERTURE_DATA_DIR` pins one library.
5. The 0.9.0 indexing card stays, with the same lines as the bar; the bar is the addition.
6. Online-only files are still downloaded as they're indexed (no change in what's read). Skipping or deferring them is
   offered as a follow-up.
7. The library order is kept in the library list (`catalogs.json`), the folder order in the library's
   `settings.json`. An older Aperture drops them on its next save (S4).
8. Pressing a folder to drag it selects it (as pressing it always has); a library drag doesn't switch.

## Design

### Video

- **`IVideoPlayer`** (App): `Open(Uri)`, `Play()`, `Pause()`, `Rewind()`, `Close()`, `IsMuted`, `Volume`,
  `NaturalSize`, events `Opened`, `Ended`, `Failed`. One player per visit, made by a factory
  (`MainWindow.VideoPlayerFactory`, settable for tests): the window's makes a `MediaElement` in code, on the first
  video, inside a host over quick view's image area (never in XAML, so a PC without a media player opens the window);
  a factory that throws counts as "can't play".
- **`VideoPlayback`** (App, pure model, `ObservableObject`, no WPF types): `IsVideoShown`, `IsReady`, `IsPlaying`
  (or "plays once ready"), `HasFailed`, `IsMuted`, `Volume`; `Show(path)` (a new player from the factory, opened with
  the saved mute and volume), `Toggle()`, `SetMuted`, `SetVolume` (raising it while muted unmutes; clamps 0–1),
  `Leave()` (stops, closes and drops the player). Events from a player other than the current one are ignored
  (V7). A mute is saved at once, a volume as the video is left. Also the input rules: `SpaceToggles` (a playable video
  is shown), `IsOnVideo(hasPicture, onPicture)`.
- **`PlaybackPrefsStore`** (Core/Settings): `{ Muted, Volume }` as JSON at a path it's given; tolerant load
  (missing, unreadable, corrupt, out-of-range → never played, muted, 0.5); atomic save (temp file, then replace); a
  failed save is swallowed. `PlaybackPrefsStore.PathFor(pinnedDataDir, librariesDir)` picks the file. App builds the
  store and hands `VideoPlayback` to the window (`MainWindow.Playback`); without one (tests), the window uses an
  in-memory store.
- **The view model** raises `QuickLookVisit` (a counter) on every `ShowQuickLookAt` and `CloseQuickLook`, with
  `QuickLookIsVideo` and `QuickLookPath` for the visit. The window drives `VideoPlayback` from the visit, never from
  `QuickLookImage`.
- **The window** (exempt shell, kept thin): `QuickLookKey` asks `VideoPlayback.SpaceToggles`; a new
  `QuickLookClick(point, clickCount)` entry point (the image area's handler calls it) toggles on a first click on the
  video, opens and pauses on a second, closes beside it; zoom input is ignored on a video. The controls bar and the
  hint line bind to `VideoPlayback`.

### Indexing

- **A reader provider:** `ApertureDatabase.ReadProvider`, a second `SqliteOrmDataProvider` over the metadata file that
  never begins a transaction, disposed with the database. `LibraryService.GetContents`, `CountForRoot` and the
  deferred prune's count read through it.
- **Tracked background reads:** `LibraryService.GetContentsAsync()` and `CountForRootAsync(rootId)` run in `Task.Run`
  and are tracked like index runs; `ShutdownAsync` waits for them. A test hook `LibraryService.ReadingContents` runs
  inside each contents read (tests hold it, or record its thread), so tests drive the real read.
- **Rows have a version:** every assignment of `_allRows` (the startup read, `LoadRows`, a refresh) bumps
  `_rowsVersion` and drops the folder index (rebuilt from those rows when next needed, or handed over prebuilt by a
  refresh). A read whose starting version is no longer current isn't applied.
- **One coalescing refresh worker** (`MainViewModel.RequestRefresh(rows, tree, countRoot)`): requests add to the
  pending work (rows, tree, a set of folders to count); one worker at a time takes it all, reads off the thread
  (`GetContentsAsync`, `CountForRootAsync`, `FolderIndex.Build`), then on the UI thread applies the counts, and the
  rows if still current (else asks for them again), rebuilds the tree if asked, and requests the off-thread grid build;
  then runs again while anything is pending. A failed read keeps what the window had. The streaming tick asks for
  rows; the climbing count for that folder's count (still gated per folder by `IntervalGate`); a run's end for rows,
  tree and its count.
- **`FolderIndex`** (Core/Library, pure): `Build(rows, hidden)`, `Subfolders(rootId, relDir)` = `FolderTree.Subfolders`
  on the same rows. `BuildTree` and `LoadChildNodes` read the current index.
- **Scan progress:** `FileScanner.Scan` takes `Action<ScanTally>`, called every 250 files found and once at the end;
  `ScannedFile.IsOnlineOnly` from `CloudFiles.IsOnlineOnly(attributes)` (offline 0x1000, recall-on-open 0x40000,
  recall-on-data-access 0x400000). The indexer reports `Processed` = found while scanning, then works out which files
  it will read (new, changed, or with stale thumbnails) before the loop, and reports `OnlineOnly` = how many of those
  are online-only.
- **`IndexingMessage`** (Core/Formatting, pure): the tree status, the headline and the friendly line, from the runs in
  progress (each folder's alias and latest report), so the view model only hands it the runs.
- **The status bar** gets a full-width 3 px `ProgressBar` along its top edge, bound to `IsIndexing`,
  `IndexIndeterminate`, `IndexValue`, `IndexMax`, and the friendly line; the card shows it too.

### Sidebar

- **`ListOrder`** (Core/Formatting, pure): `Apply(items, order, id, name, comparer)` and `Move(ids, id, toIndex)`;
  `MoveToSlot(ids, id, slot)` for a drop (a slot among all the rows, the dragged one included: a slot after it counts
  one less). Libraries sort by the current culture, folders ordinally, each ignoring case, as before.
- **Libraries:** `CatalogRegistryState.Order`, read leniently (a JSON element: strings kept, anything else ignored, so a
  bad value never sets the list aside); `CatalogRegistry.Order` / `SetOrder(ids)`; every save writes it.
  `CatalogBarViewModel.MoveLibrary(id, toIndex)`.
- **Folders:** `ApertureSettings.RootOrder` (`long[]?`, with a lenient converter: numbers kept, anything else ignored,
  so a bad value never resets the settings); `MainViewModel.MoveRoot(rootId, toIndex)` moves the `RootVm` itself,
  saves, rebuilds the tree, keeping expansion and selection.
- **Drag (window, exempt):** from a library button or a root node, past the drag distance, with private data formats;
  the slot from **`DropIndex.At(y, rows)`** (App, pure); an insertion line while dragging; `ListOrder.MoveToSlot`
  then the view model. The window's `DragOver`/`Drop` accept only `FileDrop`.
- **Counts:** **`LibraryCount.Read(dataDir)`** (Core/Storage): `null` if there's no `aperture.db` or it can't be read;
  opens it `Mode=ReadOnly`, `Pooling=False`, with a provider of its own, and counts by the open library's own code
  (`ItemStore.IncludedUnion` + `HiddenFolderStore.All` + `LibraryService.Contents`). `CatalogBarViewModel` reads each
  other library's count after each `Refresh`, one at a time under a gate that **Delete library files** also takes;
  a generation drops results from an older refresh; a changed count is recorded off the UI thread.
  `LibraryListItem.ItemCount` is observable.
